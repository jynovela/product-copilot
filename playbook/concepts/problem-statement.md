# Problem statement

## What it is

A short, evidence-based description of who has a problem, what it is and why it matters, written without a solution. Every source in the batch agrees it never names a solution. Formats: current state, consequence and ideal state (Hermanto); the 5 Ws and H; gap, orientation, impact and significance (Morelli, Miro); the d.school point of view "[Stakeholder] needs a way to [need] because [insight]"; "[Persona] struggles with [problem] when [situation], which leads to [impact]" (ProdPad); JTBD "When I…, I want to…, so I can…"; SCQA for stakeholders. (see [[2026-11-24-research-digest-problem-size]])

## How to use it

- Keep it to one to three sentences; if it needs a page, root causes or solutions have crept in (Miro, Stewart). (see [[2026-11-24-research-digest-problem-size]])
- If it has only one obvious solution, it is too narrow; naming a channel ("a better app") is already a solution (Trivedi, Hermanto). (see [[2026-11-24-research-digest-problem-size]])
- If it says "users are dissatisfied", it is too broad: which users, with what, compared to what? (noirbook, Morelli) (see [[2026-11-24-research-digest-problem-size]])
- Include a data point or two and the affected segment with a count (noirbook's template; Miro's outputs). (see [[2026-11-24-research-digest-problem-size]])
- Revise it as you learn (ProductPlan, Miro, ProdPad, Torres). (see [[2026-11-24-research-digest-problem-size]])

## Watch out for

- About 60% of founders and half of PM candidates describe a solution when asked for the problem (Trivedi, personal observation). (see [[2026-11-24-research-digest-problem-size]])
- Keep the problem document separate from any solution so you don't fit the problem to the solution (Goetzmann). (see [[2026-11-24-research-digest-problem-size]])
